# peer replies and delegated jobs

two changes. alice asks bob a question through skid. skid includes a command that bob can use to answer alice. jarvis asks bob to review a file. jarvis waits in the background. bob writes his answer once and skid returns it as soon as it is ready. if jarvis disconnects, skid keeps the answer for when it comes back.

you can open bob on your phone or laptop, type a correction, answer a question or interrupt. your correction can change his answer. jarvis receives the answer to the review it assigned. a later conversation with bob generates no report of its own. nobody labels a turn or hands over control.

## 1. skid gives bob a return address

- `skid send` and `skid start --stdin` from a skid-launched agent prepend one line, then preserve the original brief byte for byte. example copy is “alice on macbook · `skid reply 9f20ab.UMoh_1iytHZHPl87`”. the command takes the answer on stdin. bob decides whether to use it. `reply` makes one guarded send and adds no reply instruction.
- at the final provider `exec`, stamp `SKID_REPLY_TO` with one shell-safe encoding of the full pane ref, provider, pid and process start identity. use the foreground runner for managed jobs. pass it into the actual tool shell. stamped codex panes use native `--no-daemon` and a per-launch `shell_environment_policy.set` override. apply the current launch value on start, resume and fork. codex 0.171.0 keeps the first client's tool environment when another shared-daemon client rejoins its loaded conversation. the separate process keeps the same native screen, account and history and prevents inheriting that first address. concurrent writers on the same saved thread are refused by the qualified build. a missing, stale or ambiguous automatic address gives ordinary one-way delivery. two panes opening the same thread must never silently inherit each other’s address. ordinary tmux callers can use a local return address when process ancestry proves the current foreground. `--reply-to REF` supplies an explicit destination for detached callers. an off-pane send without an address goes through as ordinary text. the send receipt says whether a reply address was included. an explicit invalid address fails before writing.
- keep the full ref internal. print a unique prefix of the enrolled machine id (normally six hex digits), a dot, and the base64url encoding of the first 12 bytes of a sha-256 digest. follow the existing handle encoding, hashing the version tag, full machine id, session lifetime, pane, provider, pid and process start identity. at `reply`, resolve the prefix locally, require exactly one matching foreground on that machine, then pass its full identity to guarded send. check the identity both when issuing the address and immediately before writing. an absent or ambiguous match refuses. this keeps the printed command short without an address registry. the address names a terminal running a particular process. it carries no user authority and cannot distinguish conversations switched inside that process. validate the composed 32 kib text and 64 kib wire limits before effects. preserve separate creation and input receipts for a partial start.

`skid wait` checks the pinned pane immediately and every five seconds, for one minute by default. idle, working or needs-input can satisfy it. idle can occur between turns. `written` confirms a terminal write. neither answers a job. ## 2. jarvis gets one answer per assignment

one new tool, `agent.delegate`. the gemini api cli targets a different provider. codex and claude already expose the interfaces needed here. [gemini api cli](https://github.com/google-gemini/gemini-api-cli)

jarvis supplies the existing action id and originating conversation internally. it pins the enrolled machine through local fleet status before dispatch. the worker writes ordinary prose.

```text
new       {machine, profile, cwd, brief, model?, effort?}
follow-up {after: prior_job_id, brief}
receipt   {job_id, state: accepted}
result    {job_id, state: answered | failed | interrupted | unknown,
           answer?, reason?, terminal?}
```

`accepted` means recorded by jarvis. a follow-up gets its own id. jarvis routes it to the prior job’s host. the host resolves `after` to the same live worker and its current conversation. only one assignment runs in a worker. if the person or jarvis already started a turn, refuse the new assignment as `failed(busy)` before provider input. a closed worker returns `failed(unavailable)`. no queue. a pending approval is still the original job. jarvis can point the owner to the worker’s terminal.

| owner | contract |
| --- | --- |
| jarvis | save the action and origin before dispatch. send the action uuid and brief through the installed skid cli. the existing observer opens one background result request per outstanding job. on restart, reopen it by the same id. save the exact result and append one waking message to its original conversation in one transaction. keep ack pending until the host confirms it. repeated delivery creates one logical result. jarvis may summarize several results in one message to the owner. ordinary successful work takes zero terminal reads. |
| skid on the selected host | use the existing paired gateway and tmux. `skid job submit/result/ack` map to `PUT/GET/DELETE /v1/jobs/{id}`. reserve id and request digest in a private file before launch or input. equal resubmissions return the recorded disposition. changed input conflicts. only the winner dispatches. keep the sealed result until ack, then retain id, digest, disposition and worker ref for deduplication and follow-ups. the first job id names the worker’s socket for its lifetime. include the exact terminal ref in the submission receipt when available so jarvis can direct the owner there during work. a known before-submit refusal is a failure. an offline host stays pending. on a reachable host, a dead reservation owner or lost worker with no provable outcome resolves to `unknown`. bind ownership to process lifetime and use atomic replacement on seal. never repeat a possibly entered brief. |
| provider worker | one process per live conversation. it serves the tmux terminal and a user-private local socket for skid. it orders keyboard input and jarvis assignments at one point. claim before provider input and seal the result atomically. fence a missing id before confirming absence to the host. recover only the bound native turn when possible. provider success without final text yields `failed(no_final_answer)`. `interrupted` requires provider confirmation. partial text carries its actual disposition. keep content out of argv and logs. |

each managed codex worker starts its own `codex app-server --listen stdio://` with the selected account, cwd, tools and permissions. only the worker can write that pipe. both devices attach to its tmux pane. a stock `resume` elsewhere can write divergent history. attach through skid to operate this live worker. bind only a newly started, worker-submitted turn to its final item and completion status. managed codex disables autonomous goals, local automation and agent-message wakes to keep one input owner. an unowned active turn is busy. a recovery continuation cannot supply the answer. claude uses its agent sdk, a single in-flight root request, the native result message and its success or error status. bind a steering message to that root, use the provider’s acknowledged input boundary, and never promote an unacknowledged message to a later turn. the sdk reports synthetic starts asynchronously; an as-yet unseen internal start can race admission, while exact root and steer ids constrain attribution. distinguish provider-confirmed interruption from a lost connection. the cost of exact peer delivery is a live process check and a separate native
codex process for stamped panes. automatic sends without a proved address stay
one-way. create preflight reserves room for the widest runtime ids, so a brief
near the encoded limit can be refused before launch. a timed-out result request
opens again by id, and acknowledged jobs retain a small tombstone per
assignment to prevent replay. the worker's simple terminal shares the provider
conversation and controls, with fewer native menus. jarvis shows a bounded wake
and keeps the full answer available by receipt.

## 4. proof before release

1. **red.** write temporary end-to-end tests at the installed skid and jarvis entry points. show bob gets a bare brief and jarvis can observe idle without receiving an attributable answer. then implement.
2. **peer.** on real codex and claude tool shells across hosts, send and start preserve multiline text and supply the short return command automatically. one reply reaches the original process. a stale or colliding short address refuses. race two same-account codex panes, including concurrent resume refusal, fork while the first stays alive, and resume after close. exercise a replaced process, occupied draft, oversized message and lost write receipt. no guessed destination or repeated paste.
3. **job.** give two workers identical briefs and finish in reverse order. on a healthy connection each result returns on the open request with zero periodic status calls or pane reads. finish just before and just after a waiter attaches. restart jarvis during work, drop the connection after completion and before ack, then reopen by id. each originating conversation receives its answer once, with zero repeated submissions. cover the reservation-to-launch crash, duplicate submit, busy refusal, interruption, failure and a long multibyte answer.
4. **takeover and fleet.** steer, answer a real question, approve or deny, and interrupt from the same phone/laptop session. race a human turn against a follow-up. a later answer never completes the old job. qualify `personal`, `work`, `work2`, `claude-work`, `claude-work2` on `macbook`, `dev-server`, `arch`. check shared codex account storage and auth refresh under concurrent launches, and claude’s acknowledged steer. if every normal profile bypasses prompts, qualify approval handling on an isolated prompt-enabled launch per provider. unavailable or untested cells are `NOT_RUN`. for this rollout the owner approved macbook and the four qualified profiles on dev-server. arch and dev-server `claude-work` stay deferred. verify an installed peer reply between the two selected hosts before switching jarvis.
5. **green, refactor, rerun, delete.** build and rehearse on macbook. consolidate duplicated paths after green, then rerun affected journeys on the final revision. delete temporary harnesses and their fixtures. an independent verifier records content-free evidence and cleanup separately. live writes and release follow existing owner approval rules. this document specifies future checks.
